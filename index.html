The page that took seven seconds

Vantiva India · HomeSight Care · Architecture & implementation

Node.jsKafkaIn-memory cacheRBAC/ABACReact
The problem

Opening your account page didn't make one slow request — it made several. Each one went to the database and fetched the same slow-moving information over again, and some took seven seconds to come back. People sat and watched the page assemble itself piece by piece.

What I built

A rebuilt set of APIs that stop asking the database for things that rarely change. The information behind an account — the people on it, their home devices, the account itself — is loaded into the server's memory the moment it starts and indexed so any of it can be found instantly, with the database still behind it if something is missing. I owned the parts covering user accounts and app registration, including the screens for the second, and added role- and attribute-based permission checks across everything I moved.

How it stays current

Nothing reloads on a schedule. Every time a record changes in the database that change is published as an event, and it's applied to the copy in memory as it arrives — so the copy keeps pace continuously rather than drifting out of date between refreshes. The honest limit: if that stream of events disconnects, nothing periodically re-reads everything as a safety net, so the copy stops updating until it reconnects. Knowing exactly where that edge sits is worth more than pretending it isn't there.

The call I'd defend

I had a free hand on the architecture. The application was already tightly coupled, so breaking it into separate services would have meant paying the full cost of a distributed system up front and getting none of the benefit. I kept it as one deployable application — but structured so each area, user accounts and app registration, owns its own boundary inside it. That's the shape that lets you split a piece off later if it ever earns it, without pretending you're already there.

Outcome High-traffic responses went from roughly 7 seconds to 40–50 ms.

Telemetry into tables people can query

Vantiva India · Smart Spaces

DatabricksPySparkCassandraMedallionAWS LambdaPower BI
The problem

IoT telemetry landed in Cassandra, which is built for writes rather than for the questions analysts ask of it. Wi-Fi mesh uptime was worked out router by router, by hand.

What I built

Ingestion out of Cassandra into Databricks, then a layered setup — raw, then cleaned, then report-ready tables rebuilt every day, the pattern known as medallion — so reporting reads from a curated layer rather than from the raw device stream. On top of it, an on-demand Excel report driven by an AWS Lambda, letting site managers pull router and device performance for the last 24 hours or a custom range across 50+ sites.

The call I'd defend

Cassandra held raw rows — written for speed of capture, not for answering questions. Every KPI needed its own cleaning and segregation, and doing that work inside each report would have meant the same logic living in several places and the numbers quietly drifting apart. The medallion split does the cleaning once, in the middle, so everything downstream reads the same curated layer and agrees with itself.

Outcome Those report-ready tables feed Power BI dashboards used by a senior architect, the sales team and clients, and the same curated layer now backs ML work including churn prediction. The same reports were how we traced LoRa and Zigbee faults — routers dropping off, devices failing to sync, missing packets — supporting a ~99% uptime SLA.

A day of sensor data you can read at a glance

Vantiva India · HomeSight Care

ReactNode.jsCassandraTime bucketing
The problem

Motion and door/window sensors produced a stream of individual events. Useful for a machine, unreadable for a person — there was no way to look at a day and see the shape of it. And the person who needed to read it wasn't an operator or an analyst.

What I built

A heat map that reads sensor data from Cassandra and lays a day out in 15-minute buckets per device. Behind it sits one generalised aggregation function: which aggregation to run and which sensor to run it against both come from the request URL, so adding a sensor type doesn't mean writing new backend code.

The call I'd defend

Bucketing happens in the timezone of the home the device sits in — not the server's, and not the viewer's. That distinction is the whole thing: the person reading this is often in a different country from the person it's about. Get it wrong and someone's entire day shifts by hours, and a chart that's confidently wrong is worse than no chart at all.

Who reads it Families, not operators. Someone whose elderly parent lives back home, opening the app to see that there was normal movement this morning — delivered through a US elderly-care provider.

Ten KPIs, and what they actually mean

Vantiva India · In progress

SnowflakedbtData modellingSource-to-target mapping
The problem

The data was already in Snowflake and there was a list of ten KPIs to report on. What didn't exist was an agreed definition of what any of them meant — which is the part that quietly decides whether every number downstream is right.

What I'm building

I wrote the definitions first, starting from the literal reading of each KPI and settling each one with the business. Then the groundwork underneath: working out what a single row in each source table actually represents, agreeing the business meaning, and mapping every source field to where it lands. The models that will run the pipelines are being built on that foundation now, in dbt.

The call I'd defend

Definitions before models. It's slower at the start and it looks like nothing is being built — but a reporting table whose meaning was settled up front is one people still trust a year later, and one nobody has to re-argue every time a number looks wrong.
